Cause de l'écart gate(80) vs JSON(79) :
  tools/dxf_pipeline/gate_sanite.py scanne TOUS les fichiers
  assets/profiles/*.json, y compris index.json lui-même, qu'il traite
  comme un 80e "SKU" nommé "index" (statut_gate=SUSPECT_GEOMETRIE,
  motif CONTRAT_LOADER_STATUT_NON_OK car index.json n'a pas de champ
  "statut"). Ce n'est pas un vrai SKU catalogue. Après exclusion de
  cette ligne parasite : 79 SKU JSON == 79 SKU gate. Écart expliqué,
  pas de blocage. gate_sanite_rapport.csv régénéré à neuf pendant cette
  passe (python3 gate_sanite.py) : diff strictement vide avec la
  version déjà commitée -> rapport confirmé À JOUR (non périmé).

Cause de l'écart .stp(100) vs JSON(79) :
  - 72 SKU JSON ont un .stp/.step correspondant (après normalisation
    des noms irréguliers : suppression suffixe "sans motif"/"-sansmotif"
    et "plan", extension .step traitée comme .stp).
  - 7 SKU JSON n'ont AUCUN .stp/.step : 0900, 1000, 1005, 1102BH, 1145c,
    1202, 20-54. Cause identifiée : ces profils proviennent d'une source
    différente du pipeline STEP — champ "source.fichier" = *.dxf (0900,
    1000, 1005, 1145c, 20-54) ou *.stl (1102BH, 1202), jamais *.stp/.step
    (voir champ source.methode="section_step" absent pour ces 7).
  - 28 fichiers .stp/.step (D113, D113M, D563, D567, D568, D579, D601,
    D605, D606, D611, D615, D624, D625, D629, D632, D656, D657, D702,
    D707, D749, D802, D820, D880, D887, D892, PLIN08, PLIN08M, PLIN10M)
    n'ont PAS (encore) de JSON associé : backlog de traitement du
    pipeline d'extraction, jamais traités en JSON à ce jour — cause
    identifiée (pas une anomalie, un simple retard de traitement batch).
  Total réconcilié : 72 + 7 = 79 JSON ; 72 + 28 = 100 .stp/.step.
  AUCUN écart résiduel non expliqué.

     CONTRAT_LOADER_PLAFOND_VIDE (indices de face de pose vides malgré

     /tmp/p15_catalogue_publication.csv, colonne cause_divergence.
